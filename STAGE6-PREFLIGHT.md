# Stage 6 — Pre-flight brief (canonical statements, signed invoices, QR/URI, XMR-only pricing)

Prepared 2026-10-14 (background research, after Stage 5 passed its full
§22 gate and the first encrypted-orders design review arrived partial).
Nothing here is a decision or a ratification. Items marked RATIFY are
Cameron's as spec owner, in the sheet at the end. This brief's job is to
stop Stage 6 from being built on the pre-review order flow by accident:
part of Stage 6 is untouched by the review, and part of it sits exactly
where the review changes things.

## Scope (spec §24 stage 6)

Canonical statement library (§10, as amended), `signed-invoice` module,
invoice page, QR code, payment URI, `xmr-only` pricing.

## What the Stage 5 gate leaves ready

- Workspace verified 239 passed / 0 failed (Stage 5 report, corrected
  figure — the 143/143 first reported was a partial run; dev DB is back
  on the standard port 5432).
- §10 amendment rules already ratified 2026-10-13: integers ASCII digits
  only, no sign/whitespace/leading zeros, u64 + range checks; timestamps
  RFC 3339 parse → canonical re-format → byte-identity, leap seconds
  rejected; `network:` closed set of three, must match instance config;
  destinations validated via the single `Subaddress` newtype (Q17: no
  success type carries kind/network as strings); public IDs pinned to
  `^(mkt|inv|ord|pool|acct)_[0-9a-f]{32}$` with matching prefix.
- Form-layer normalization is exactly one function
  (`normalize_form_lines`), exactly once; nothing below it trims, and
  statements are signed over server-generated bytes built from
  already-normalized strings — so QR/URI generation inherits that rule
  and must not gain a second normalization path.

## Safe to build regardless of the Step A / Step B ratification

These do not depend on how orders are encrypted or when payment is
verified, and no reading of the partial review touches them:

1. The canonical statement library itself (parser + serializer +
   byte-identity rules above), including regenerating all §10 examples
   at the pinned 32-hex ID length, as the amendment already requires.
2. The `InvoiceStatement` / `PoolStatement` destination typing via
   `Subaddress` (Stage 7 consumes the pool side; the type lands now).
3. QR code + payment URI generation from an already-validated invoice
   statement (deterministic bytes in, deterministic URI out).
4. `xmr-only` pricing as the sole pricing mode until Stage 11
   (`seller-quoted-rate` is a later stage, unchanged).

## Hold — intersects Step A / Step B (do NOT build on the old flow)

The partial review (DESIGN-REVIEW-RESPONSE-1-PARTIAL-2026-10-14.md,
truncated at source in §4 Phase 6, mid-sentence; authorship unconfirmed
— Cameron sent two reviews, ChatGPT and Claude, and which wrote this
one is not recorded; the second review has NOT arrived — the uploaded
file was the request pack itself) recommends, with verdict
"adopt with changes" for both steps:

- **Seller-signed acceptance before payment** is the review's required
  missing piece: a committed order + payment proof alone establishes
  neither acceptance nor fraud. If ratified, a signed acceptance
  statement becomes a new canonical statement type — it belongs in the
  Stage 6 library's design from the start, not bolted on after the
  invoice format locks.
- **Signed reservation certificate** for address assignment (binds
  protocol version, marketplace ID, random reservation/order ID, buyer
  + seller fingerprints, listing-version digest, assigned address +
  network, issuance time, reservation policy). Also a new signed
  statement type, and it needs a public-ID prefix — the pinned pattern's
  prefix set (mkt|inv|ord|pool|acct) has no reservation prefix.
  Never recycle an exposed address, even after apparent abandonment;
  expiry must not destroy the evidence binding.
- **Versioned, signed listing snapshots.** Stage 2 listings are mutable
  today; an order committing to a listing-version digest requires
  immutable listing versions. That is a Stage 2/Stage 6 seam — decide it
  before invoice/order binding, not during.
- **Randomized commitments, split by domain:** C_terms, C_shipping and
  C_order as H(domain || 256-bit random secret || length-delimited
  encoded content), secrets independent per part. A bare hash of
  predictable terms is explicitly not hiding.
- **Core lifecycle shrink (Step A correction):** if a paid
  acknowledgement is a core-visible transition, the platform learns a
  sale occurred. For the "no verified happy-path sales ledger" property,
  acknowledgements/completions stay inside encrypted messages and the
  core's lifecycle is routing + disputes only. This touches the gated
  Stage 4 order state machine — under gate discipline that makes it a
  spec amendment first (like the §17 orders-route ruling), never a
  silent Stage 6 side-change.
- **Pre-payment checklist + exportable evidence bundle are REQUIRED
  mitigations** in the review, not optional docs — the buyer-side
  counterpart to Stage 5's encryption guide. If Step A is ratified,
  these are Stage 6/8 deliverables with a named home.
- **Privacy wording corrected** to the weaker exact claim: ordinary
  orders encrypted; no verified happy-path sales ledger; disputes
  disclose what they disclose; communication, address-assignment and
  public-listing metadata remain visible. No liability-reduction claim
  without jurisdiction-specific legal advice. This wording belongs in
  the threat model / Limitations copy when ratified.

## Explicitly rejected by the review — keep out of later stages

- Monero timelocked-to-self bond: rejected on protocol facts (custom
  unlock times deprecated; relay already rejects them). Do not let it
  re-enter Stage 9 reputation design.
- Blind-signed completion tokens: rejected for v2 reputation (they
  authenticate eligibility, not completion).
- Countersigned completion receipts as a denominator: omit from v2, or
  label strictly as attestations; never a "verified sales" count, a
  fulfilment percentage, or a Bayesian reliability estimate. The
  indistinguishability result: no hard-to-fake completed-sales
  denominator and no honest positive trust score exist under the
  constraints. What survives for Stage 9: reasoned, severity-based
  negative findings (one proven deliberate deception can justify
  removal; a service breach is not fraud; human review + appeal before
  permanent removal), continuity shown separately and never labelled
  trading success, and scoped, signed, expiring endorsements.
