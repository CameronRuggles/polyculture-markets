# Polyculture Markets — Buyer Tx-Proof Payment Flow

**Purpose of this document.** A self-contained design record, written to be
handed to another Claude instance (or any reviewer) for independent review.
It describes a payment-confirmation protocol for a noncustodial Monero
marketplace: what problem it solves, the mechanism, the exact rules, the
invariants it keeps and the ones it deliberately changes, its current
implementation status, and the questions still open. No other document is
required to follow it, though file and commit references are given for
verification against the repository (github.com/CameronRuggles/polyculture-markets).

---

## 1. The problem

Polyculture Markets is noncustodial: buyers pay sellers directly,
wallet-to-wallet. The server assigns one pre-generated, wallet-signed
subaddress per order from the seller's pool and never touches keys,
funds, txids, or amounts. In the original design (Direct Payments v1),
the only path to the Paid state was the **seller's attestation** — the
seller sees funds arrive and marks the order paid.

An external payment-path audit (2026-10-18, against commit `22a1eb5`)
found the hole this creates (its finding **H1**, severity High):

- A buyer who pays a seller who then stays silent has **no recourse**.
  The dispute guard required a buyer-report record tied to an invoice;
  direct orders have no invoices, and nothing ever wrote that record
  for them. The Dispute button rendered, and the payments-risk page
  promised a dispute — but the action always failed.
- At 48 hours, an automated sweep cancels unpaid orders. A paid order
  whose seller never attested is cancelled, after which it cannot even
  be reviewed. The seller keeps the money; the record shows a plain
  cancellation.
- The state machine also let a **seller cancel from the
  awaiting-payment state with no evidence at all** — so a seller could
  take payment and cancel, in one click.

In short: the party who performed (the buyer) had no way to put their
performance on the record.

## 2. The mechanism: Monero transaction proofs

A Monero **transaction proof** (OutProof) is generated by the sender's
wallet from the per-transaction key the wallet stores for transactions
it sent. Verified against a specific address (any wallet software can
do this — `check_tx_proof`; no chain sync, a per-transaction lookup
plus a local signature check), it attests:

- this transaction paid **this specific address**,
- **this exact amount** (e.g. 0.1 XMR), and
- its confirmation count.

Because every order is assigned a **unique subaddress used for nothing
else**, a valid proof for that subaddress at the order's amount *is*
proof of payment for that order. There is nothing else it could be
paying for.

What a tx proof does **not** reveal, to anyone it's shown to:

- the buyer's balance (that would be a *reserve proof*, a different
  feature, not used here),
- the buyer's other transactions, other addresses, or change outputs,
- anything about the buyer's keys.

Contrast with the alternative considered — seller **view keys**: a
private view key lets the holder derive all of a seller's subaddresses
and watch *every* incoming payment to that wallet, past and future,
across every marketplace and personal use. It is surrendered in
advance, cannot be un-shared, and forces every independent operator to
run always-on scanning wallets. For software whose purpose is many
independent marketplaces, view keys are the wrong primitive and
proofs are the right one: one payment, disclosed after the fact, by
the party who made it.

## 3. The protocol

Actors: buyer, seller, marketplace server, moderators.

1. **Order created.** The server assigns an unused subaddress from the
   seller's signed pool (allocation at creation, never reused; this
   step is unchanged from v1).
2. **Buyer pays** the subaddress directly from their own wallet.
3. **Buyer submits the proof** (txid + proof string) to the
   marketplace. Submission is the evidentiary act:
   - The order advances to **Paid** on the strength of the evidence
     (see §4 for how this coexists with the state machine's rules).
   - The 48-hour unpaid sweep can no longer touch the order.
   - The seller can no longer cancel or decline the order.
   - The seller now owes shipment.
   - The buyer may submit **at any point while the order is open**,
     including after trouble appears — protection is not limited to
     buyers who file paperwork in advance.
4. **Seller confirms receipt per order, per subaddress.** Confirmation
   is bound to one specific order and its assigned subaddress (the
   ground truth the seller's own wallet shows them). There is no bulk
   or account-level confirmation. The seller then ships and marks the
   order shipped, as before.
5. **Buyer can dispute** — after shipment as in the existing flow, and
   now genuinely before it too, because the report/proof record exists.

**Fallback.** A buyer who cannot produce a proof may still manually
confirm "I paid." That records a weaker claim (BuyerReported, §4): it
opens the dispute path but does **not** mark the order Paid, stops
neither the sweep nor a seller declaration. In the UI it sits behind
the proof path, which is presented first, prominently, with
instructions — see §7.

## 4. Evidence ladder and the state machine

The order state machine has an evidence ordering; only the core moves
an order to Paid, and only on sufficient evidence:

`None < BuyerReported < BuyerProofSubmitted < SellerAttested < ProofVerified / WalletObserved`

The new rung, **BuyerProofSubmitted**, is the design's centre:

- A bare buyer report (BuyerReported) still can **never** mark an
  order Paid. This invariant is load-bearing and unchanged: no one
  reaches Paid on their own say-so.
- A buyer-submitted **proof** can — not because the server trusts the
  buyer, but because the submission is a *checkable artifact*: anyone
  with wallet software (the seller, a moderator) can verify it
  against the subaddress in seconds. The server's record is only as
  strong as the artifact's checkability, and the artifact is on file.
- `ProofVerified` remains reserved for an actual verification event by
  a party running wallet software. The server itself **never verifies
  and never labels anything verified** (see §6).

## 5. Visibility: the seller never sees the proof

An owner-directed rule, with a game-theoretic reason. If proof status
were visible to the seller, sellers could sort buyers into protected
and unprotected tiers and selectively scam the unprotected. Therefore:

- The seller **never sees** the proof, the txid, or any marker that
  one was submitted. Their pages and notifications never receive the
  data at all (enforced structurally, not by display logic).
- A proof-paid order reads to the seller **identically** to one they
  confirmed themselves — same wording ("Seller confirmed payment"),
  same state, same notifications; their confirm control renders on
  every Paid order so even its presence signals nothing.
- The proof is visible only to the buyer who submitted it (their own
  order page) and to **moderators**, in the dispute and review-flag
  contexts.

Combined with late submittability (§3.3), a would-be selective
scammer gains no usable information: a buyer who looks unprotected
can arm themselves retroactively the moment the seller misbehaves.

## 6. What the server does and does not do

Unchanged from the noncustodial design:

- The server never holds keys, seeds, or funds; never moves money;
  runs no wallet and no node.

Deliberately changed, by owner decision:

- The server now **stores the buyer-submitted txid and proof string**
  for orders where a buyer submits them (previously it stored no
  txids at all). This is bounded: one transaction per order, disclosed
  by the buyer for exactly this purpose, visible per §5.
- The server stores them **verbatim and unverified**, labeled
  buyer-submitted. Verification is performed by humans in their own
  wallet software (seller on receipt; moderator in review/dispute).
  Server-side automatic verification was considered and left out —
  it would require chain access on the server and contradict the
  public limitations statement that the instance "runs no wallet."
  It remains a possible future extension (spec Stage 8) behind an
  explicit owner decision.

## 7. Escalation: review flags and the not-received declaration

Two automatic flags feed the existing moderator review queue:

1. **Proof without confirmation.** A proof submission with no seller
   confirmation raises a review flag immediately. It clears
   automatically when the seller confirms. (Visibility, not
   accusation: most flags resolve when an honest seller checks their
   wallet.)
2. **Contradiction.** A proof on record **and** a seller not-received
   declaration (below) raises a flag immediately. Both claims cannot
   be true; a moderator verifies the proof and the record settles on
   a hard fact.

**Seller not-received declaration.** After 48 hours (the same horizon
as the unpaid-order sweep), a seller may declare non-receipt for a
specific order and subaddress:

- No proof on file → the order closes as unpaid (the seller-initiated
  equivalent of the sweep). A manual buyer report on file does not
  block closure, but stays on the record, and the buyer keeps a
  dispute path that reopens the order.
- A proof on file → the declaration does **not** close the order; it
  raises the contradiction flag (above).

## 8. Buyer experience and wallets

The payment page leads with proof submission and how to produce one.
Verified-easy paths (checked 2026-10-18):

- **Feather (desktop):** History → right-click the transaction →
  Create Tx Proof → "Prove payment to an address" → "Get formatted
  proof" copies the complete packet. Feather also verifies proofs
  (Tools → Verify transaction proof).
- **Monero GUI (desktop):** History → the "P" button on a transaction
  yields the payment proof; Advanced → Prove/Check verifies.
- **CLI:** `get_tx_proof` / `check_tx_proof`.

**Cake Wallet (Android/iOS) is the weak spot, stated honestly:** a
one-tap formatted proof export could not be confirmed from Cake's
documentation. Cake buyers can reach transaction details, but the
smooth path today is a desktop wallet. The buyer guidance names the
confirmed wallets rather than inventing steps for Cake.

## 9. Invariants — kept and changed

Kept:

- Server never touches keys, funds, or amounts of others' payments;
  no escrow; no fees introduced.
- A buyer's unverified word never marks an order Paid.
- Only the core transitions order state; evidence levels gate the
  Paid transition.
- One subaddress per order, never reused; assignment race-free.
- The server never labels anything "verified" that it did not verify;
  it verifies nothing.
- Seller-side blindness to proof existence (§5).

Changed (owner decision, 2026-10-18, recorded in
`SPEC-V2-AMENDMENTS.md`):

- Buyer-submitted txids and proofs are stored (§6).
- A new evidence rung, BuyerProofSubmitted, can carry an order to
  Paid (§4).
- Dispute gating for assignment-carrying orders is report/proof
  existence rather than the invoice-tied 72-hour rule (which remains
  in force for assignment-less orders).
- Closed orders' pay pages show no payable address ("This order is
  closed. Do not pay."; the QR route returns 404).

## 11. Residual edge and open questions

**Residual edge (known, not yet closed).** Protection starts at
submission. A seller cancel or the sweep landing *before* a paid
buyer's first submission can still close the order, leaving the proof
with no live order to attach to. The candidate fix is a
**revive-on-proof window** (a proof submitted within N days reopens
an order closed unpaid). Awaiting the owner's decision, including
the window length.

**Open owner questions from the audit:**

1. Address assignment at order creation (current) vs at seller
   acceptance (no burned addresses, no pay-before-acceptance, but
   the buyer waits on the seller).
2. Server-side signature/proof verification: acceptable to run an
   offline verifier (no keys, no network egress) despite the
   "runs no wallet" limitations line — or keep all verification in
   human hands as this design does?
3. (Subsumed above) paid-but-expired handling → the revive window.
4. Address-change protections: pause length on orders after a seller
   changes their primary payment address (24h? 72h?), and whether a
   certified change (old address signs the new one) skips the pause.

**Not yet built (audit fix brief):** task 2 (verify batch signatures
at upload — server-side; depends on question 2 and amending a locked
test assumption that currently pins "no signature-format check"),
task 3 (step-up authentication + notice for payment-identity changes;
depends on question 4).

## 12. What a reviewer should scrutinize

- §5's blindness: is there *any* seller-observable channel (timing,
  notifications, page structure, error behaviour) that leaks proof
  existence?
- §4's new rung: does BuyerProofSubmitted create any path where a
  fabricated proof string (never actually verified by anyone) causes
  a real-world obligation before a human checks it? Who bears that
  risk, and is the flag latency (§7.1) an adequate control?
- §7.2's declaration: can a seller use declarations strategically
  (e.g. declaring against manual-report buyers to chill reporting)?
- §6's stored txids: retention, access scope, and whether storage
  should expire after terminal state + dispute windows close.
- The revive window (§11): does reopening closed orders create
  reputation or accounting inconsistencies?
