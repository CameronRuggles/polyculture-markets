# Spec v2 — Amendments from the Stage 0 Decision Review

Adopted 2026-10-13. Cameron adopted spec v2 as the build basis (Q9) and confirmed
the Opus decision-review verdicts (log: `DECISIONS-LOG-2026-10-13.md`). Where an
amendment and the original spec text disagree, the amendment wins. Section numbers
refer to the spec.

## §1 / positioning (Q9)
- Orders carry a `settlement` field, always `direct` in v2; the order state machine
  must leave room for a future escrow state without a schema migration that rewrites
  history. The retired October model (multisig-first, WASM plugin economy) is
  reference material for §21, nothing more.
- AGPL compliance is automatic: the page footer Source link serves the running
  build's exact source tarball from the instance itself (must work over onion).

## §3 invariants (Q2, Q14)
- Destination validation order is pinned: decode/checksum → network → kind.
  Locked tests may assert exact error codes (§3.7).
- Destination validation additionally requires both embedded public keys to be
  torsion-free and not the identity (curve25519-dalek predicates on the
  decompressed points). Canonical-encoding rejection is provided by the `monero`
  crate's `PublicKey::from_slice` (verified against its source) and must not be
  reimplemented — but a locked fixture for the non-canonical case stays in the
  suite permanently, so a future crate version dropping that check fails CI
  instead of silently reopening the hole.

## §4 modules (Q4-S1, Q17)
- The API defines a `Subaddress` newtype constructible only through the core
  validation function. `InvoiceStatement.destination` and
  `PoolStatement.addresses` use it. One validation function; no module-local copies.
- No success type carries `kind` or `network` as strings (Q17): a validated
  `Subaddress` exposes its network only as the closed `Network` enum. Kind and
  network appear only inside rejection types — `WrongKind { found: AddressKind }`
  with `AddressKind` a closed enum {Standard, Integrated, Subaddress}, and
  `WrongNetwork`. (The Stage 0 spike contract's `DestinationInfo.kind: String`
  is deleted; see `marketplace/docs/api-contract.md`.)

## §7 accounts (missing-question, Stage 1)
- Admin/moderator accounts require TOTP (works without JavaScript) and admin routes
  live on a separate listener (already in §19 HTTPS profile; now a requirement in
  all profiles that expose admin functions).

## Form input (Q13)
- Trimming happens exactly once, in one named function at the form layer
  (`normalize_form_lines` in the API contract): pasted multi-line input is split
  on line breaks, ASCII whitespace (space/tab/CR/LF) is stripped from line ends,
  empty lines are dropped. The same function normalizes tx-proof `txid`/`proof`
  fields. Rationale: browsers submit textarea newlines as CRLF, so strictness at
  the form boundary would reject every pasted address pool.
- Non-ASCII whitespace and invisible characters (NBSP, zero-width space, BOM,
  format characters) are REJECTED with a specific "contains invisible
  characters" error — never silently stripped.
- Nothing below the form layer trims: not destination validation, not the
  statement parsers, not the database, not URI/QR generation. Statements are
  signed over server-generated bytes built from already-normalized strings, so
  no second normalization path exists.

## §9 orders (Q3, Q9)
- `settlement` field per above. Integer range rules from §10 amendment apply to
  quantity (≥ 1).
- Listing description size bound (owner ruling, 2026-10-14): a listing
  description is at most **20,000 characters**; validation rejects longer
  descriptions with the description error. (The spec previously said only
  "within the size bound" without a value; the Stage 2 blind suite's
  oversize test — 1,000,000 characters — was `#[ignore]`d pending this pin
  and activates unchanged on it.)

## §17 routes (owner ruling, 2026-10-14)
- `GET /orders` is a declared route: the orders collection page (the §15
  global header's "Orders" entry). Login-required — any authenticated
  account; anonymous actors get `LoginRequired`. The handler performs
  object-level filtering: a caller sees only orders where they are the
  buyer or the seller. `authorize()` gains this route with the
  any-authenticated class, alongside the already-declared `POST /orders`,
  `GET /orders/{id}`, `GET /orders/{id}/terms.txt`, and the order-action
  POSTs. (The Stage 4 draft web layer already served this page while §17
  did not declare it; the retrofit gate made `authorize()` deny it. This
  amendment resolves the deviation in favour of declaring the route.)

## §10 canonical statements (Q3, Q4, Q15)
- Every integer field: ASCII digits only, no sign, no whitespace, no leading zeros,
  fits in u64; then range checks (amount > 0 and ≤ configured max; address-count
  1–200; quantity ≥ 1).
- Timestamps: parse with the `time` crate's RFC 3339 parser, re-format in the fixed
  canonical format, require byte-identity; leap seconds (`:60`) rejected.
- `network:` is a closed set of three values in the parser; the core also rejects
  statements whose network differs from the instance's configured network.
- The statement parser validates destinations via the `Subaddress` newtype and
  checks each against the statement's `network:` line (invoices and pools alike).
- Public ID patterns are pinned (fixing the §10-example vs §16 inconsistency):
  `^(mkt|inv|ord|pool|acct)_[0-9a-f]{32}$` with the matching prefix per field type.
  All §10 examples are to be regenerated at this length.

## §12 payment evidence (Q12, missing-questions)
- Destination submissions (pool + invoice) are cross-checked with a second parser:
  `validate_address` on the verify-only wallet RPC (reference C++ implementation).
  Disagreement ⇒ reject + security event.
- Flag policy (Stage 8, recorded now): `untrusted: true`, `in_pool: true`, or a
  reorg dropping confirmations below the minimum must never yield ProofVerified.
  No "verified" label may render anywhere until real stagenet verification is
  proven (hard gate).
- Unverified-path homework (Q11): SEIPD v2 acceptance is proven against the
  RFC 9580 Appendix A test vectors (A.3 sample v6 cert, A.8 X25519 AEAD-OCB
  message) plus a derived hidden-recipient v6 variant — independent vectors,
  never self-generated fixtures — before the envelope suite locks. The legacy
  no-integrity reject path is closed by the Q7a synthetic tag-9 fixture.

## §14 messaging (Q1, Q5, Q6, Q16)
- Integrity-protected forms accepted: SEIPD v1 (MDC), RFC 9580 SEIP v2, and
  LibrePGP AED (tag 20) — tag 20 special-cased **by name**, with a hand-check of
  its fixed header (version 1; cipher AES-128/192/256; AEAD mode OCB or EAX; sane
  chunk-size octet). No other unknown packet is ever accepted in the container
  position.
- PKESK/SEIP version pairing enforced: v3 PKESKs → SEIPD v1 or tag 20; v6 PKESKs →
  SEIPD v2 only. Mixed sequences rejected.
- The 64 KiB cap measures submitted bytes (armored or binary), enforced as a
  per-route body limit before multipart parsing or armor decoding.
- Packet limits made concrete: parser configured to never descend into containers;
  on the visible top-level sequence — 1–8 PKESKs; exactly one encrypted container
  and nothing after it; no top-level SKESK/marker/compressed/literal/signature
  packets; no trailing bytes after the armor footer; Padding (tag 21) rejected
  until a real client emits it.
- Error taxonomy (ordered, first failure wins): `Empty`, `NotEncrypted`,
  `Malformed`, `UnsupportedPacket`, `HiddenRecipient`, `RecipientKeyRetired`,
  `WrongRecipient`, `ExtraRecipient`. There is deliberately no
  registered-vs-unknown recipient distinction (membership oracle). Rejected
  plaintext is never echoed into a form and never logged. `ExtraRecipient` shows
  the offending key ID only, never an owner.
- `RecipientKeyRetired` is conversation-scoped (leak fix, 2026-10-13): return it
  only when the matched key was the recipient's current key at some point during
  THIS conversation — i.e. the sender was already shown it. Otherwise the result
  is `WrongRecipient`. Buyer key history is not public; an unconditioned variant
  would let a counterparty probe whether a harvested key ID ever belonged to the
  buyer. Locked test: probe a buyer's retired key in a conversation that never
  saw it → `WrongRecipient`.

## §16 database (Q9, Q15, Q16 storage)
- `orders.settlement` column (`direct` in v2). Public IDs per the pinned patterns.
- Key history storage (Q16 prerequisite, owner check 2026-10-13):
  `identity_keys` records each key's validity interval (`created_at` when it
  became current, `retired_at` when it was rotated away, `status`), and
  `key_rotations` records every rotation with its type and date. In addition,
  a `conversation_key_sightings` table records every time the server presents
  a participant's key inside a conversation: (conversation, key owner,
  fingerprint, key ID, shown-to account, time). Stage 5's envelope validator
  decides `RecipientKeyRetired` vs `WrongRecipient` from sightings plus
  validity-interval overlap with the conversation — never from key history
  alone, and never in a way that reveals a key the sender was not shown.

## §19 deployment (missing-questions)
- Clock source must be specified despite the no-outbound rule (NTP allowance or
  Tor-based time) — Stage 10 deliverable, flagged at Stage 4.
- Key-file lifecycle (generation, separate backup, rotation, loss consequences) is
  a Stage 4 design item, documented in `docs/operations.md`.

## §22 process (Q7, Q8, Q10, Q12)
- Locked-suite fixture constructions may change only with the owner's sight of the
  diff; assertions never. (Q7a constructions pre-approved: synthetic tag-9 legacy
  fixture; `--compress-algo none` oversize fixture.)
- Constructed Monero address fixtures expire when the suite locks: real fixtures
  from `monero-wallet-cli --stagenet --offline` before locking; the valueless
  stagenet seed is committed for Stage 8 reuse.
- Sequoia backend is Nettle in dev, CI, and production; CI fails any build enabling
  the experimental/variable-time RustCrypto features.
- Dependency rules: `cargo vet` audits for `monero`, `sequoia-openpgp`, and Nettle
  bindings on every bump; security fixes land within days; other bumps of those
  crates are standalone tasks that re-run the full locked suite. Toolchain pinned
  via `rust-toolchain.toml`.
- Stage gates for stages 1–10 (stagenet, no public users) may be satisfied by an
  independent-model review pack (fresh context, spec + diff only, file:line
  evidence per invariant, paired `cargo-mutants` runs) — never for changes to
  locked tests or invariants (owner reads those as plain-language assertion
  lists), and never for the go-live gate (human external audit).
- `marketplace-id` generation and persistence across onion/domain migration must
  be specified in Stage 0 (see threat model open items) — every signed statement
  binds it.
- Gate pace (owner's ruling, 2026-10-13 late): stages 1–3 — built before their
  gates existed — are retrofitted first, in this order: (1) these amendments and
  the API-contract revision land before any blind authoring; (2) blind suites
  for stages 1–3, beginning with Stage 1's route-by-role authorization matrix;
  (3) failures are fixed in the code, never in the tests (fixture *constructions*
  only, owner's sight of the diff, assertions unchanged); (4) `cargo-mutants`
  on the auth and key code, and one review pack per stage. From Stage 4 on,
  gate-as-we-go: **no stage starts until the previous one passes its gate.**

## Direct Payments v1 (owner handoff, 2026-10-15)

Adopted 2026-10-15 with the owner's "Direct Monero Payments v1" handoff
and the mapping in `DIRECT-PAYMENTS-V1-PLAN.md`. Where this section and
the original spec text disagree on the payment path, this section wins.

- **(a) Payment signatures are Monero wallet signatures.** For the
  payment path, the §10 OpenPGP-signed canonical statements are
  superseded by per-subaddress wallet signatures: each pool subaddress
  carries the one-line message
  `xmr-direct-v1|<marketplace_id>|<network>|<seller_id>|<primary_address>|<subaddress>`
  signed by the seller's primary address key (wallet `sign`), stored
  and served byte-exact, and verified by the buyer in their own
  wallet. §10 PGP statements remain live for key rotation (Stage 3)
  and terms files (Stage 4); the Stage 6 statement library stays in
  the tree but leaves the payment path. The instance
  `marketplace_id` for payments is **`vespiary-market`** (env
  `MARKETPLACE_ID` override kept). No server-side signature
  verification in v1 (setting exists, default off).
- **(b) Stage 8 scope shrink.** Tx-proof evidence is deferred
  indefinitely — not scheduled. Seller attestation ships in this
  release: the seller marks an order Paid by submitting a
  `SellerAttestation { amount_atomic: None }` claim through the
  compiled-in `direct-v1` module (`DestinationProvider` +
  `PaymentEvidenceProvider` traits); the core performs the
  AwaitingPayment→Paid transition. No amounts or txids are recorded.
  Paid direct orders render as **"seller confirmed payment"** — the
  word "verified" must not appear as a payment claim anywhere.
- **(c) Destination assignment at order creation.** For the direct
  strategy, one unused pool subaddress is assigned atomically at
  order **creation** (not at invoice issuance after seller accept),
  taken oldest-first under a per-seller row lock. An assigned address
  is never reused: cancel, decline, or expiry retires its pool entry.
  The Stage 4 accept gate changes accordingly: for orders with an
  assignment, accept requires the assignment (which holds by
  construction); orders without an assignment keep the issued-invoice
  check unchanged. Direct-v1 writes no rows into `invoices` (its
  statement column is the §10 PGP contract); assignment, batches, and
  attestations live in the additive migration-0008 tables
  (`payment_identities`, `payment_batches`, `payment_pool_entries`,
  `payment_attestations`), and every pool address also lands in the
  global `destinations` table (source `pool`) so the existing UNIQUE
  constraint enforces no-address-ever-reused. `address_pools` (PGP)
  is untouched.
- **(d) Primary-address change = presentation reset.** Changing the
  payment primary address retires all unused pool entries, stamps the
  identity's `changed_at`, and shows a "payment identity changed"
  banner/marker on the seller profile and payment pages for 30 days
  (configurable). Order and review history is **never erased** —
  counterparties' records and dispute evidence depend on it. First
  set has no banner.
- **(e) No-payment-identity compatibility rule + scoped drain
  defences (deviation with rationale).** Allocation at creation is
  attempted only when the seller has a payment identity. Identity
  but empty pool ⇒ order creation is refused with a "seller needs to
  add payment addresses" error and the listing page shows that state.
  No identity ⇒ the order proceeds without an assignment exactly as
  before this release (pre-payment behaviour; the Stage 4 locked
  suites exercise this path), and such orders have no payment page
  content (the pay page states payments are not set up). Rationale:
  it keeps the locked Stage 4 surface and every pre-payment seller
  working unchanged while payment-enabled sellers get the full
  one-address-per-order guarantee. The drain defences (per-buyer 10
  order-creations/hour, max 3 open unpaid) count **only**
  assignment-carrying orders, because their purpose is pool
  protection; the <24h-account cap is unchanged and applies to all
  orders. Unpaid-order expiry (48h, configurable) is served by a
  minimal in-process sweep; the general scheduler remains Stage 10.
- **(f) seller_id rendering for payment messages.** Accounts are
  `acct_<32 hex>`, but payment messages require `[a-z0-9-]`, so the
  payment seller_id is **`acct-` + the 32 hex chars**, derived by one
  function in one place (`app::payments::payment_seller_id`) used by
  the dashboard display, batch validation, and the canonical message
  rebuild. The instance network for payments is **stagenet** (config
  `INSTANCE_NETWORK`); payments accept only the instance network.

## Stage 9: moderation is closure, not exclusion (owner ruling, 2026-10-16)

Owner, verbatim: **"Banning is impossible so it's useless to offer it as a tool.
Account closure/deletion or whatever however makes sense."** This supersedes any
suspension/ban language anywhere in the spec and in earlier drafts of the Stage 9
plan:

(a) **There is no ban, no suspension, and no re-entry blocklist.** Repeat
    accounts are unprovable; the marketplace does not pretend to exclude a
    person. The registered "re-entry / retired-fingerprint blocklist" question
    is RESOLVED by this ruling: not built, in v1 or later, unless the owner
    reverses the ruling explicitly. No code, schema, or copy may implement or
    imply exclusion of a person.
(b) **The account-level moderator action is CLOSE ACCOUNT.** Closure ends the
    identity — the real asset on this marketplace (PGP key history, account
    age, reputation): the account cannot log in (a property of closure), its
    sessions are revoked, its published listings are unpublished (→ `paused`),
    its unused payment-pool entries are retired, its profile is marked
    "account closed" with the date, and its reputation stops accruing (no
    facts for orders terminating after closure).
(c) **History is retained.** Order and review history is never deleted by
    closure and stays visible to counterparties — their records and dispute
    evidence depend on it. Counterparties holding non-terminal orders receive
    an inbox notice that the account closed.
(d) **Self-service closure** (account settings, passphrase + typed
    confirmation) runs the same code path as moderator closure, with the
    account itself as actor.
(e) **Honest copy rule:** no page may claim or imply the person cannot
    return. Closure copy says the identity and its accumulated history ended.
(f) Unchanged Stage 9 scope: warn (a record + signal, not a restriction),
    listing removal/restore, reports + queue, dispute outcomes, and TOTP
    step-up gating on every moderator action (closure included). Moderators
    have no power over funds and no conversation-browsing interface, ever.
