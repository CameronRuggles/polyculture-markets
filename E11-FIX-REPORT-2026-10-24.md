## What changed

Commit `48a2329` — `seller-helper/helper-cli/src/main.rs`:
- `cmd_status` returns `Result<bool, String>`; the bool is set
  when a per-trade row is `Err` (printed as `{trade_id}  ERROR:`).
  The status output itself is byte-for-byte the same as before;
  only the process code changes. `run_core` threads the bool;
  `main` maps it to exit 2. All other core commands map to
  `false`.
- The five usage-error sites return `EXIT_RUN_FAILED` (1)
  instead of 2, with a comment recording the allocation so 2 is
  never reused. `fail()` uses the same constant.
- The in-code E11 comment that recorded "per-trade ERROR rows
  keep exit 0" is rewritten to the ruling; the store-level
  paragraph is kept (that case stays exit 1).
- USAGE text gains an EXIT CODES section (0/1/2 as above) — the
  helper's in-tree CLI documentation. No other doc needed
  changing: SELLER-GUIDE documents only `check`'s codes, which
  are unchanged and still accurate.

Commit `d130e8d` — tests, `helper-cli/tests/cli_ht.rs` (+3):
- `status_with_an_error_row_among_clean_trades_exits_2` — two
  trades in one store; control run asserts exit exactly 0 with
  both `state=Assigned`; one trade's held assignment signature
  is replaced with the seller's signature over wrong bytes;
  the run then exits exactly 2, the clean trade still prints
  its state row, the broken one prints `ERROR: … does not
  verify`.
- `status_with_a_foreign_signed_assignment_exits_2` — the E4
  shape specifically: the buyer's held assignment is re-signed
  by a third key that is neither party's; buyer status exits
  exactly 2 with the ERROR row naming the signature failure.
  Control before the plant: exit exactly 0.
- `run_level_failures_exit_1` — `buyer verify` with a missing
  assignment file exits exactly 1 ("cannot read"); an unknown
  mode and a no-argument invocation exit exactly 1 (the
  normalised usage paths).
- Comment-only amendment in
  `status_over_an_unreadable_store_prints_the_error_row_and_fails`:
  its header comment stated the superseded "per-trade rows keep
  exit 0" shape. The comment now records the ruling; **no
  assertion in any existing test was changed or weakened.**

## Decisions / collisions surfaced (not silently resolved)

1. **Usage errors were 2.** That collided head-on with
   reserving 2 for ERROR rows; per the ratified semantics they
   are run-level failures and are now 1. Any script that
   treated helper exit 2 as "usage error" will now see 1 —
   that is the intended break, and it is why the ruling pairs
   the two changes.
2. **`buyer verify` refusal stays exit 1.** Verify emits no
   per-trade rows — a refusal (including its signature check)
   is the command's own failure, and it already exited 1
   before this change (it never exited 0 on a refusal). The
   E4-must-exit-2 rule is applied where the foreign signature
   appears *as an ERROR row*: the status fold over a held set.
   If the owner wants a refused verify to exit 2 as well, that
   is a one-line change on top of this branch — flagged here
   rather than folded in silently.
3. **Legacy `seller check` keeps 0/1 as an answer code**
   ("not in this wallet" = 1), unchanged: it emits no rows,
   and its codes are documented behaviour in the seller guide.
