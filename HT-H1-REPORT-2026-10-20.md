## Spike verdict — stated plainly

**Acceptance by the reference wallet binary was NOT obtained in this
sandbox. The construction is proven correct against the reference
algorithm; the binary's own proof path is broken in this rig for
every transaction, including its own.**

What was done:

- `helper-core` builds OutProofV2 proofs from txid + transaction
  key(s) + address + message alone, following Monero 0.18.3.4's
  `generate_tx_proof` construction exactly (prefix hash, shared
  secret D = s·view, R = s·spend for subaddresses, the `TXPROOF_V2`
  domain separator, Schnorr pair (c, r)).
- Real stagenet-form transactions were created on a local private
  fork (Monero 0.18.3.1 Ubuntu binaries): a 1 XMR payment to a
  subaddress (tx `2cdb091c…fd8522`, key `25f05791…47dc08`) and a
  0.5 XMR payment to a standard address (tx `d75cbbd0…552e7`, key
  `e6374004…7d330b`). Proofs were built for both from key material
  alone; both parse back to a single segment.
- A faithful Rust port of the reference checker — Monero 0.18.3.4
  `crypto.cpp` `check_tx_proof` plus wallet2's output scan
  (derivation = 8·D, `P_i = Hs(derivation‖i)·G + B`) — **accepts
  both proofs**, **rejects** the same proof under a wrong message,
  and finds the paid output derivable from each proof's shared
  secret.
- The reference binary path could not be made to render any verdict:
  the rig's daemon returns `prunable_hash` = 64 zero chars for every
  transaction (self-mined, pool-resident, after chain export/import,
  and after `monero-blockchain-prune`), and its wallet throws
  "Cannot calculate the hash of a pruned transaction" before
  evaluating any proof — critically, **the wallet's own
  `get_tx_proof` for its own transaction fails identically**, so the
  rig can neither produce nor check any proof. The failure is in the
  rig's binaries, not in the proof.

Gate consequence, applied as specified: the transaction-key proof
path ships only on a passing spike, so **no H1 command exposes it**.
`build_out_proof_v2` remains in helper-core (proof intake commands
arrive in later stages) with the spike status documented at the
function. **Owner item: re-run binary acceptance against a real
stagenet node before H2 wires proof intake.**

## Environment notes (for whoever runs the next gate)

- Two gate runs were discarded in full, per the standing rule: one
  launched while the app suite was still running against the same dev
  DB (cross-suite interference), and later runs that failed because
  **Postgres had died — /tmp (512 MB tmpfs) was exhausted by a
  sibling task's scratch**, which also broke initdb. The security
  suite is state-sensitive: it passes on a pristine DB and its
  Direct-Payments pool tests fail against a DB the app suite has
  already run against. That isolation property predates H1; the
  reliable order is: rebuild the DB, run security first, or rebuild
  between suites.
- The dev Postgres was relocated out of /tmp: binaries and data now
  live under `/home/pguser/` (`pgsys/`, `pgdata/`), same port 5432,
  same `DATABASE_URL`. `~/tmp-build/reprovision.sh` still describes
