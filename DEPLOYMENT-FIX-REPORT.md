## Task 3 — Unprivileged builds and migrations (DM3)

**Changes — `deploy/deploy-demo.sh` restructured (commit `5dd3671`):**
- **Cargo never runs as root.** Two sanctioned shapes: (a) `MARKETPLACE_BIN_DIR` installs prebuilt binaries and builds nothing on the host; (b) otherwise the build runs **as `MARKETPLACE_BUILD_USER`** (default `$SUDO_USER` — the account whose `~/.cargo` holds the toolchain) inside a throwaway `tar` copy of the tree (excluding `target/` and `.git`), and only the finished binaries are installed. With neither available, the script **dies with an explicit refusal** ("refusing to run cargo as root: set MARKETPLACE_BUILD_USER=… or MARKETPLACE_BIN_DIR=…"). A build user of `root` is refused by name.
- **Migrations run as a dedicated role.** New role **`marketplace_migrator`** (NOLOGIN) owns the `marketplace_demo` database; migration marker table, migration application, and the app-role grants all execute via `SET ROLE marketplace_migrator` in the psql session. The postgres superuser is used only to create the two roles + the database, set the app role's password, set database ownership, and — for databases created by the old script — `REASSIGN OWNED BY postgres TO marketplace_migrator` when (and only when) public-schema tables are still superuser-owned (guarded by a count query; no-op on fresh installs). The app role keeps DML-only rights, as before.
- Safety properties kept and re-proven: mainnet/production refusal on the *effective* env, env file `0600` and never overwritten once present, idempotent re-runs, loopback health check, binary SHA-256 printed. Also: the script now creates `blobs/` alongside `media/` under the state dir.
- Runbook §4/§5 rewritten to the new interface (password file, build user or prebuilt dir, migrator-owned migrations); its stale step list was the only doc describing the old behavior.

**Verification — what was proven here:** a new stubbed harness, **`deploy/tests/test-deploy-demo.sh`** (committed), runs the real script with cargo/psql/su/systemctl/curl as logging stubs against a scratch source tree. Against the **old** script it demonstrated the audit's findings live (7 failures: cargo ran as root; `sed` errored on the hostile password and the env kept `CHANGE-ME`; the psql role call died on an unterminated quote from the password's `'`). Against the **new** script: **15/15** — T1 mainnet refused before any build; T2 refuses to run cargo as root (and names why); T3 prebuilt run succeeds with cargo never invoked; T4 build mode succeeds with cargo's recorded uid = the build user's (1000), never 0; T5 an existing env is byte-identical after a re-run.
**Documented-but-unverified:** a full live redeploy on a real host (explicitly out of scope). Specifically unexercised against a real host: systemd starting the service under the new unit (Task 5), a real `cargo build` inside the script's throwaway copy (the harness's cargo is a stub; the workspace build itself is verified separately, and the script's exact `cargo build --release --locked -p app -p media-worker` invocation is the one the runbook has always used), real psql executing the migrator-role SQL (the SQL shapes and the password mechanism are proven — see Task 4 — but the role/ownership choreography itself has only run against stubs), and the `REASSIGN OWNED` migration path on a genuinely old-script-created database. First real run should be watched with the harness green as the pre-flight.

## Task 4 — Password handling (DL1)

**Changes:** the password is read from **`MARKETPLACE_DB_PASSWORD_FILE`** (the `MARKETPLACE_DB_PASSWORD` env var remains as a warned fallback). It reaches PostgreSQL as a **psql variable**: the script writes a mode-`0600` temp SQL file containing `\set pw '<escaped>'` + `CREATE/ALTER ROLE … PASSWORD :'pw'` and runs `psql -f` on it — the value is never in an SQL literal, a `sed` pattern, or any argv (the temp file is also removed by the exit trap). The env file's `DATABASE_URL` line is spliced whole-line with **awk** (no substitution of the password into a pattern at all), the password **percent-encoded** byte-wise (unreserved characters literal, everything else `%XX`), written via a pre-created `0600` file so the secret never sits in a world-readable temp.

**Verification — actually exercised:**
- Harness T3 with password `p'a"s$/\&x` (the full DL1 hostile set: `' " $ / & \`): the installed env's `DATABASE_URL` percent-**decodes back byte-exact**; the raw password appears neither in the env file nor in any recorded psql argv; the recorded psql input uses `:'pw'` and contains no literal password interpolation; env mode is `0600`.
- **Live cryptographic round-trip** against a scratch PostgreSQL 16.4 instance (port 5433, `password_encryption=scram-sha-256`, an hba line requiring SCRAM for the test role): a Python emulation of psql's documented `\set`-unescape + `:'pw'` literal substitution — replicating the script's `sql_escape` exactly — created the role with that password; the stored verifier was SCRAM; **SCRAM authentication with the exact hostile password succeeded, and with a mutated password was rejected**. (Emulation was necessary because this sandbox has no `psql` binary at all — see Task 1. The script-side shapes are pinned by the harness; the server-side semantics are proven here against real PostgreSQL.)
**Documented-but-unverified:** real `psql` performing the substitution on a deployment host (no psql exists in this sandbox). The two documented substitution rules the emulation followed are psql's own (backslash escapes inside `\set` values; `:'var'` substitutes as a quoted literal), and the escaping function is four lines, mirrored character-for-character in the proof.
